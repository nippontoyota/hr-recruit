# Technical Test Link Regeneration Design Spec

- **Author**: Antigravity Assistant & Engineering Team
- **Date**: 2026-11-18
- **Topic**: Safe Technical Test Link Regeneration Pipeline
- **Status**: Approved Design (Ready for Implementation Planning)

---

## 1. Background & Problem Statement

In the HR recruitment platform, technical tests are administered via secure public tokens generated per evaluation (`EvaluationToken`).
Currently, `POST /api/v1/evaluations/{eval_id}/token` reuses existing unexpired tokens where `is_used == False`.

If a candidate:
- Starts the 8-minute countdown timer (`test_data.deadline_at`), and time runs out or their connection drops, or
- Misplaces their link, or
- The recruiter updates the position/designation and needs to issue a fresh test,

the system currently continues returning the previous expired or active token. There is no mechanism to revoke the old token and safely issue a new link.

Recruiters need a safe, explicit way to **Regenerate Link** from the candidate's evaluation widget without breaking any existing workflows.

---

## 2. Safety & Security Requirements

1. **Strict Invalidation of Old Links**:
   When a link is regenerated, all previous unused tokens for that evaluation must be marked `is_used = True` and have their `expires_at` timestamp set to the current UTC time. Any attempt to use the previous link immediately returns HTTP 404/400.
2. **Evaluated Status Guard**:
   If an evaluation is already completed (`evaluation.status == 'EVALUATED'`), regenerating a link is strictly rejected with HTTP 400. This prevents accidental tampering with or resetting of already graded tests.
3. **Accidental Click Prevention (Confirmation Modal)**:
   In the UI, clicking "Regenerate Link" must present an explicit confirmation modal warning that previous links will be permanently invalidated and any active candidate test session will be terminated.
4. **Clean Session & Fresh Test Paper**:
   The new token must assemble a fresh question paper snapshot for the chosen position/designation and experience, with no pre-existing `deadline_at` or `started_at` in `test_data`.
5. **Audit Trail**:
   Each regeneration action must record an `ActivityLog` entry capturing the actor (`user.full_name`) and timestamp.

## 3. Backend Specification

### Endpoint Modification
- **Route**: `POST /api/v1/evaluations/{eval_id}/token`
- **Query Parameters**:
  - `position: str | None = None` (existing)
  - `regenerate: bool = False` (new)
- **Role Permissions**: `ADMIN`, `HO_HR`, `LOCAL_HR` (existing)

### Execution Flow
1. Fetch evaluation and verify authorization via `get_candidate_for_user(..., write=True)`.
2. Check `evaluation.status`:
   - If `evaluation.status == EvaluationStatus.EVALUATED`:
     - Raise `HTTPException(status_code=400, detail="Cannot regenerate link for an already evaluated test")`.
3. If `evaluation.type == EvaluationType.TECHNICAL_TEST`:
   - Update candidate's applied position with `_assign_test_position(candidate, position)`.
4. Check `regenerate` flag:
   - **If `regenerate == False`**:
     - Retain current behavior: lookup unused unexpired token. If present, update questions if timer hasn't started and return existing token.
   - **If `regenerate == True`**:
     - Find all existing active tokens for this evaluation (`EvaluationToken.evaluation_id == eval_id`, `EvaluationToken.is_used.is_(False)`).
     - Set `is_used = True` and `expires_at = datetime.now(UTC)` on all matching tokens.
     - Fall through to generate a new token.
5. **Generate New Token**:
   - Call `generate_secure_token()`.
   - Call `assemble_for_candidate(db, candidate)` and serialize to `test_data` via `to_test_data(...)`.
   - Instantiate new `EvaluationToken`:
     - `evaluation_id = eval_id`
     - `token = token_str`
     - `is_used = False`
     - `expires_at = datetime.now(UTC) + timedelta(days=settings.technical_test_link_expire_days)`
     - `test_data = test_data`
   - If `regenerate == True`:
     - Create an `ActivityLog` record:
       - `candidate_id = candidate.id`
       - `activity_type = ActivityType.SYSTEM`
       - `title = "Technical Test Link Regenerated"`
       - `description = f"Technical test link regenerated by {current_user.full_name}."`
       - `created_by_user_id = current_user.id`
     - Add log to session.
   - Commit transaction, refresh new token, and return `new_token`.

## 4. Frontend Specification

### API Client
- In `frontend/src/api/evaluations.ts`:
  - Update `generateEvaluationToken`:
    ```typescript
    export const generateEvaluationToken = async (
      evalId: string,
      position?: string,
      regenerate?: boolean
    ): Promise<EvaluationToken> => {
      const params = new URLSearchParams();
      if (position) params.append('position', position);
      if (regenerate) params.append('regenerate', 'true');
      const qs = params.toString() ? `?${params.toString()}` : '';
      const response = await request('POST', `/evaluations/${evalId}/token${qs}`);
      return response.data;
    };
    ```

### UI Component Updates (`frontend/src/components/candidates/EvaluationStageWidget.tsx`)

1. **State**:
   - `regeneratingLinkId: string | null`
   - `showRegenerateConfirm: boolean`
2. **Button Placement**:
   - Inside `TechnicalTestPaperWidget` next to `Copy Test Link` and `Send Link`:
     - Visible only when `ev.status !== 'EVALUATED' && !isReadOnly`.
     - Button text: **Regenerate Link** with `RefreshCw` icon.
     - On click:
       - Verify designation selected (`requireDesignation()`).
       - If valid, open `showRegenerateConfirm`.
3. **Confirmation Modal**:
   - Uses `<Modal isOpen={showRegenerateConfirm} onClose={() => setShowRegenerateConfirm(false)} title="Regenerate Technical Test Link?" size="md">`.
   - Content:
     - Warning banner/text: *"Regenerating will immediately invalidate all previous test links. If the candidate is currently taking the test, their session will be terminated and they will need to use this new link."*
     - Cancel button.
     - Confirm button ("Yes, Regenerate Link") with loading spinner while `regeneratingLinkId` is active.
4. **Action Handlers**:
   - Upon confirmation:
     1. Invoke `generateEvaluationToken(ev.id, designation, true)`.
     2. Construct public link `${window.location.origin}/test/${tokenData.token}`.
     3. Copy link to clipboard.
     4. Show success toast: *"New test link generated and copied to clipboard!"*.
     5. If WhatsApp modal state is present, update `waShareLink`.
     6. Close confirmation modal.

## 5. Verification & Testing Plan

1. **Unit & Integration Checks**:
   - Call `generate_evaluation_token` with `regenerate=False`: returns existing active token.
   - Call with `regenerate=True`: verify previous token has `is_used == True` and `expires_at <= now()`.
   - Verify public lookup `/public/{old_token}/test-start` fails with 404.
   - Verify public lookup `/public/{new_token}/test-start` succeeds with fresh timer.
   - Verify `regenerate=True` fails with 400 when `evaluation.status == 'EVALUATED'`.
   - Verify `ActivityLog` contains the event.
2. **Frontend UI Checks**:
   - "Regenerate Link" button appears when test is pending/not evaluated.
   - Clicking without designation shows toast prompt to select designation.
   - Clicking with designation opens confirmation modal.
   - Canceling closes modal with zero changes.
   - Confirming generates new link, copies to clipboard, shows success toast.
   - Button is disabled/hidden when test is `EVALUATED` or read-only.
